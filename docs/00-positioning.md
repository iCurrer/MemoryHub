# 定位与差异化

> 版本：2026-11-24 ｜ 对应阶段：阶段 0（立项）

## 一句话

**MemoryHub 是个人 AI 记忆的治理层**：采集、裁决、留痕、备份、检索。它不生产记忆，它管理记忆的**可信度**。

## 为什么"治理"是空位

把市面上的方案按两个维度摆一下：**存储形态**（是否人类可读）与**是否有治理**（来源/时效/审核/回滚）。

```
                有治理
                   │
   Zep/Graphiti ●  │  ● MemoryHub（目标位）
                   │
   ────────────────┼────────────────  人类可读 →
                   │
      mem0 ●       │  ● Basic Memory
      Letta ●      │  ● Obsidian / 纯 Markdown
                   │
                无治理
```

- **Basic Memory** 已经把"Markdown 为真相源 + SQLite 索引 + MCP 读写 + Git 友好"做到 1.0，且是 AGPL 开源。**这一格已经有人占了，重做没有意义。**
- **Zep / Graphiti** 有治理（双时态），但代价是正文进入图数据库，不再是可 git diff 的纯文本。
- **mem0 / Letta** 是给应用开发者的记忆基础设施，不是给个人的记忆资产。

空位是：**纯 Markdown 的形态 + 治理能力**。这就是 MemoryHub 唯一值得做的位置。

## 三个具体差异点（可验证，不是口号）

| 差异点 | 实现方式 | 可验证的判据 |
|---|---|---|
| 来源可追溯 | 每条记忆记录 `source_adapter` / `source_path` / `source_kind` / `source_hash` | 任意一条记忆都能回答"它从哪个文件的哪个版本来的" |
| 时效可裁决 | `valid_from` / `valid_until` / `supersedes` / `superseded_by` | 冲突时不覆盖旧条目，而是封窗并建立取代链，可回溯决策历史 |
| 治理自动化 | 三级信任 `auto` / `review` / `blocked` + Git 可回滚 | 日常使用不需要逐条点批准，但每条改动都能一键还原 |

## 刻意的非目标

1. **不做回写分发。** 这是原策划书 V0.1 的核心功能之一，我们砍掉。理由见 ADR-002。
2. **不做"给一个 memory.md 让所有 AI 都读"。** 那个方案已经在 2023 年就失败了：文件太长、无法分类、无法审核。
3. **不做知识管理。** 不做笔记、不做双向链接图谱、不做阅读器。用户的笔记应该在 Obsidian 里，我们只治理"关于用户的记忆"。
4. **不做多设备实时同步。** v0.x 只做备份与恢复。多设备合并是独立的分布式问题，不要在第一版碰。

## 目标用户（按优先级）

1. **同时用 2 个以上 AI 编程工具的个人开发者** —— 痛点最直接，且能自己判断工具好坏，是最好的早期用户。
2. **重视数据所有权的本地优先用户** —— 不接受把个人偏好交给云记忆服务。
3. **自建 Agent 的自动化爱好者** —— 需要一个稳定的个人上下文接口（MCP）。

**不是目标用户**：企业团队（需要权限体系与审计合规，另一个产品）、纯聊天用户（内置记忆够用）。

## 成功判据

不是 star 数，是这三个：

1. 作者本人连续使用 30 天，且停用会感到不便。
2. 有非作者用户在 GitHub issue 里描述自己真实的记忆冲突场景。
3. 能回答"这条记忆为什么是这个值"，且答案里带来源和时间。

## 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 被 Basic Memory 顺手做掉 | 治理功能对它是自然的下一步扩展 | 保持窄：只做治理，不与它竞争存储与检索；甚至可考虑兼容它的 vault 格式 |
| 上游文件格式变动 | Codex / Claude 的记忆文件位置和格式随版本变化 | 适配器声明能力、启动时探测、失败即降级为"用户手动指定路径" |
| 治理本身成为负担 | 用户不愿审核 | 三级信任 + 默认自动入库 + Git 兜底，把人工介入压到每周一次 |
| 单人维护带宽 | 阶段 2-6 工作量不小 | 严控范围：不做 UI、不做多设备、不做云端 |
