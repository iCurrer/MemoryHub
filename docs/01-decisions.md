## ADR-001 混合记忆：不替换原生记忆

**状态**：已采纳（2026-11-24）

**背景**：可以有两种做法——让用户关闭各工具的原生记忆，统一由 MemoryHub 供给；或保留原生记忆，MemoryHub 只做上层治理。

**决策**：保留原生记忆。MemoryHub 只读采集各来源，中央库作为统一治理层。

**理由**：强行接管原生记忆的失败模式很明确——工具更新后记忆机制变化，用户会同时失去原生能力和中央库。混合模式解耦了"上游变化"和"我方可用性"。

**代价**：数据会重复（同一条偏好在两处存在），必须靠去重和来源标记控制噪音。

**复审时点**：阶段 2 采集适配器完成后，评估重复率是否可接受。

## ADR-002 不做回写分发（推翻原策划书 V0.1 的核心功能）

**状态**：已采纳（2026-11-24）

**背景**：原策划书第 3.2 节把「中央库 → 外部工具」的双向分发作为三大同步关系之一，并规划了 `exports/codex/`、`exports/claude/` 等目标目录。

**决策**：v0.x **不向任何 AI 工具的原生记忆文件写入内容**。只做两件事：只读采集；生成单向只读快照（`exports/`），由用户自己决定是否引用。

**理由**：

1. 收益低。工具读取 `AGENTS.md` / `CLAUDE.md` 时只需要"能读到"，不需要"被别人格式化写回"。写回并没有多提供任何能力。
2. 风险高。原策划书第 7.3 节自己列出了同步循环、版本震荡、覆盖用户手写内容三类故障，且承认需要来源标记、目标排除、哈希识别三层防护才能压住。这三层防护的成本接近整个采集模块。
3. 污染用户资产。用户手写的一条规则被程序覆盖，是最容易失去信任的失败方式，一次就够。

**代价**：用户如果想在 Codex 里看到中央库的最新结论，必须手动引用 `exports/` 文件，或者（阶段 5 之后）通过 MCP 查询。体验上有一步摩擦。

**复审时点**：阶段 5 MCP 上线后，如果真实使用中 MCP 无法覆盖某个工具，再单独立项评估该工具的写回。

> **2026-11-25 复审启动（未改变结论）**：MCP 已上线，所有者报告的真实摩擦是「别的 AI 不会主动来查」，即本条「代价」里写的那一步。方向定为**受管区块**：在各工具入口文件里用 `<!-- MEMORYHUB:BEGIN -->` / `<!-- MEMORYHUB:END -->` 包住生成内容，区块外永不触碰、可整块删除、重跑幂等。这样能消掉理由 3（污染用户资产），理由 2（同步震荡）靠幂等替换处理。**尚未实现**，实施前需要单独立项，见 ADR-016。

## ADR-003 三级信任替代逐条人工审核

**状态**：已采纳（2026-11-24）

**背景**：原策划书要求所有 AI 产出的提案都进入待审核区，人工批准后才写入正式库。

**决策**：按风险分级：

| 级别 | 触发条件 | 行为 |
|---|---|---|
| `auto` | `category` ∈ {preference, knowledge} 且 `sensitivity` = normal | 直接入正式库，靠 Git 可回滚 |
| `review` | `category` ∈ {profile, decision}，或 `confidence` 低 | 进 `inbox/pending`，等人批 |
| `blocked` | `sensitivity` ∈ {sensitive, secret} | 阻断，禁止批准，除非先降级敏感标记 |

规则实现见 `models.py::MemoryEntry.infer_trust`。

**理由**：逐条审核在真实使用中必然崩溃——记忆增长速度高于人工审核速度，队列一积压用户就会绕过工具，工具的约束力归零。而"可回滚"是可以长期维持的：Git 提供了比人工审核更强的兜底，代价是发现问题晚一点。

**代价**：低风险类别可能被错误内容污染，需要用户偶尔查看 `git log`。为此必须在阶段 2 提供"最近变更摘要"，否则回滚能力等于不存在。

**复审时点**：阶段 4 审核流完成后，用真实数据统计 `auto` 条目的错误率。

## ADR-004 阶段 1-3 不做 Web UI

**状态**：已采纳（2026-11-24）

**背景**：原策划书规划了 8 个管理页面（总览 / 来源 / 待审 / 记忆库 / 同步 / AI Provider / 备份 / 设置）。

**决策**：阶段 1-3 只提供 CLI。审核用 `list` + `show` + `approve` + `git diff`。Web UI 推迟到阶段 6，且必须以"自用一个月后仍想打开"为前提。

**理由**：UI 是单人项目最大的时间黑洞。8 个页面的信息架构在自用之前无法确定，先做等于先猜。CLI 的 `git diff` 在审核场景下比任何自研界面都强——它已经有成熟的差异高亮、逐行追溯和回滚。

**代价**：外部用户第一次上手会不习惯。缓解方式是 `doctor` + 明确的错误信息，而不是提前做界面。

**复审时点**：阶段 4 结束后，记录一周内用户实际执行了哪些审核动作，据此决定 UI 内容。

## ADR-005 阶段 1 零第三方运行时依赖

**状态**：已采纳（2026-11-24）

**背景**：原策划书建议的技术栈是 Pydantic + Typer + Watchdog + SQLite + FastAPI。

**决策**：阶段 1 的 `src/memoryhub/` 只用标准库。具体替换：

| 原方案 | 阶段 1 实现 | 迁移时点 |
|---|---|---|
| Pydantic | `dataclasses` + 手写 `validate()` | 阶段 3（校验 AI 结构化输出时引入） |
| Typer | `argparse` | 阶段 4（命令数量增长后评估） |
| PyYAML | 自研 frontmatter 最小解析器（扁平 key + 内联列表） | 阶段 2（需要 Obsidian 互操作时引入） |
| SQLite | 目录扫描 | 阶段 2（引入 FTS5 + trigram 分词） |

**理由**：零依赖意味着在任意一台装了 Python 3.11 的机器上 clone 即可运行、可测试，不需要先解决依赖安装。这对单人项目的迭代速度是决定性的，也让 CI 极简。阶段 1 的真正目标是验证数据结构，不是验证库选择。

**代价**：frontmatter 只支持受限 YAML 子集（不支持嵌套与多行字符串），手写解析器有维护成本。`.md` 文件目前不能保证被 Obsidian 正确解析——这一点在阶段 2 必须解决，否则"人类可读"这个核心卖点不成立。

**复审时点**：阶段 2 开始时立即复审，特别是 PyYAML 的迁移。

**部分取代（2026-11-24，P2-01）**：本 ADR 关于"阶段 1 零第三方依赖"的部分**仍然成立**（阶段 1 已按此交付并归档），但"PyYAML → 自研最小解析器"这一行**已被取代**：`frontmatter.py` 现由 PyYAML 实现，`pyproject.toml` 声明 `pyyaml>=6.0`。

取代的理由不是"想用库"，而是实测出了三类真实故障，自研解析器无法在不重写的前提下修掉：

1. **读不出**：Obsidian 写出的块列表（`tags:` 换行 `  - dev`）会导致该条记忆整条不可读。
2. **写不对**：`tags: [123, null, true]` 这类字符串在往返后变成 int/None/bool；`source_path: *alias` 这种以 `*` 开头的值在真实 YAML 解析器里是语法错误。
3. **不支持策划书自己的 schema**：§6.2 的 `source:` 是嵌套映射列表，自研解析器直接拒绝。

新实现的三个偏离（记录在此，避免以后当成 bug"修"掉）：

- 用 YAML 1.2 的布尔规则（只有 `true`/`false`），否则名为 `on` / `yes` 的标签会变成 `True`；
- 时间戳统一还原为 ISO 8601 **字符串**（YAML 会把它解析成 `date` 对象，而 schema 要求字符串）；
- frontmatter 里的**重复键直接报错**，不静默取最后一个。

**新增代价**：`AGENTS.md`「验收方式」里"测试必须能在无第三方包的机器上跑通"这一条对阶段 2 不再成立，测试现在需要 `pyyaml`。该文件由所有者维护，本 ADR 只记录冲突，不代为修改。

## ADR-006 时序字段是差异化核心，不是可选增强

**状态**：已采纳（2026-11-24）

**背景**：原策划书第 7.4 节把冲突处理定义为"展示差异，交用户判断"，没有引入时效模型。

**决策**：`valid_from` / `valid_until` / `supersedes` / `superseded_by` 是**必填语义**，不是可选元数据。旧结论不删除，而是关闭有效期并建立取代链，`status` 转 `archived`。实现见 `VaultStore.stamp_validity`。

**理由**：用户真正的问题不是"我忘了什么"，而是"这条还算数吗"。删除式更新会永久丢失"当时为什么这么定"，而这恰恰是审计价值所在。选择在 Markdown frontmatter 里实现而不用图数据库，是为了保住 git diff 的可读性——这是与 Zep/Graphiti 的关键分野。

**代价**：查询时必须过滤 `valid_until`，检索逻辑比"读最新"复杂；条目数量会随时间单调增长，需要归档策略。

**复审时点**：阶段 3 冲突检测完成后，验证取代链在真实数据上是否会被正确维护。

## ADR-007 代码与数据物理分离

**状态**：已采纳（2026-11-24）

**背景**：原策划书第 6.1 节的目录树把 `vault/` 放在项目根目录内。

**决策**：代码在 `D:/project/MemoryHub`（可开源），数据在 `D:/my-memory`（独立私有仓）。vault 路径通过配置 / 环境变量 / CLI 参数三级解析，任何情况下不写死。

**理由**：

1. 混在一起的第一个后果是 `.gitignore` 越写越长，第二个后果是某次 `git add -A` 把私人记忆提交进公开仓。
2. 采集监控、Git 备份、开源发布三件事作用对象完全不同，共用目录会让每一件都变脏。
3. vault 若落在被采集的来源目录内，会直接触发同步循环。

**代价**：用户需要理解"两个目录"的概念，`init` 必须解释清楚。

**复审时点**：不复审，这是硬约束。

## ADR-008 路径与命名规范

**状态**：已采纳（2026-11-24）

**决策**：

- 代码：`D:/project/MemoryHub`（首字母大写，与 GitHub 仓名一致）
- 数据：`D:/my-memory`（全小写、中性命，不随工具改名而失效）
- 两处均为纯 ASCII、无空格。

**理由**：Watchdog 文件事件、PyInstaller 打包、subprocess 调用 Git 三者对空格与中文路径的处理均不稳定。数据目录名与工具名解耦，是因为工具名本身就是暂定的。

**代价**：无。

**复审时点**：不复审。

## ADR-009 阶段 1.5 加固：写不丢、读不藏、门禁可判定

**状态**：已采纳（2026-11-24）

**背景**：阶段 1 骨架通过评审后发现三处会在**正常使用路径**上丢数据或失联，且验收门禁本身自相矛盾：

1. `new_id()` 用「秒级时间戳 + 4 位 hex」＝ 65536 种后缀。实测同一秒内生成 2000 个 id 出现 32 个重复；`save()` 直接原子覆盖，重复 id 会**静默覆盖**前一条。批量导入（阶段 2 适配器的 `read() -> list[MemoryEntry]`）正是这个模式。
2. frontmatter 解析失败时 `iter_entries()` 只往 stderr 打一行警告就跳过该条；用户在 Obsidian 里把 `tags: []` 改成块列表 `tags:\n  - dev`，这条记忆就会从 `list`/`search` 里**无声消失**，`show` 还会抛 traceback。这与「Markdown 人类可读、可手改」的定位直接冲突。
3. `doctor` 把「config 未生成」「vault 未 git init」也算 FAIL，而 `init --no-git` 是文档化选项 —— 四处文档写的「必须无 FAIL」在合法路径上不可达。

**决策**：

| 编号 | 决策 | 落点 |
|---|---|---|
| 1 | id 后缀扩到 8 位 hex，且新增 `VaultStore.create()`：id 已被占用则抛 `IdCollisionError`，绝不覆盖 | `models.py::new_id`、`markdown_store.py::create` |
| 2 | `save()` 保留 upsert 语义（状态流转需要覆盖同一 id），但加一层 `_refuse_foreign_owner` 兜底：同一 id 的 `created_at` 不同即判定为他人条目，拒绝写入 | `markdown_store.py::save` |
| 3 | 读失败一律显式上报：`scan()` 返回 `(entries, errors)`，`list`/`search` 打一行汇总警告，`stats` 输出 `unreadable`，`doctor` 判 FAIL | `markdown_store.scan`、`cli.py` |
| 4 | `doctor` 分三级：`FAIL` 阻断门禁（Python 版本、vault 缺失、layout 缺失、条目不可读）/ `WARN` 不阻断（config 未生成、git 未初始化、vault 位于 OneDrive） | `cli.py::cmd_doctor` |
| 5 | 补齐 ADR-003 明文规定但未实现的规则：`confidence == low` 归入 `review` | `models.py::infer_trust` |
| 6 | 查询默认过滤 `valid_until` 已过期的条目（ADR-006 的「查询时必须过滤」），历史视图用 `--include-expired` 显式打开；显式 `--status` 视为历史查询，不再二次过滤 | `models.is_expired`、`cli.py` |
| 7 | `--approve` 遇到 `trust=review` 必须拒绝，需显式 `--force` 才能越过；`blocked` 仍不可越过 | `cli.py::cmd_new` |
| 8 | `--vault` 在子命令前后都接受，任一缺省不再覆盖已解析的值 | `cli.py::_vault_parent` |

**理由**：这 8 条里没有一条是功能，全部是「让已有的承诺真的成立」。第 1、2 条防的是静默数据丢失 —— 一次丢数据就够让用户不再信任这个库；第 3、4 条防的是「工具说没事，实际有事」，它比报错危险得多；第 5、7 条是把 ADR-003 从文档变成代码，否则「分级信任」这个核心差异点在任何一次 `--approve` 面前都不存在。

**代价**：

- id 变长一点，旧 vault 的 4 位 id 继续可读（正则接受 4–32 位），但不会自动迁移。
- `scan()` 会把整库读进内存，大于数万条时应换成流式统计（阶段 2 索引上线后此路径不再是主路径）。
- 默认过滤过期条目改变了 `list`/`search` 的返回集，这是行为变更，需在 README 中写明。
- `--approve` 变严格后，原有的批量脚本若依赖它直接入库会失败 —— 这是有意的。

**复审时点**：阶段 2 采集适配器落地后复审第 1、2 条（批量导入是碰撞的唯一真实场景）。

## ADR-011 输入是异构的：格式基线 + 两个字段扩展

**状态**：已采纳（2026-11-24，所有者批准三条建议；当天实现）

**背景**：核实上游来源后（证据与置信度见 [`04-upstream-formats.md`](04-upstream-formats.md)），三件事与现有设计不符：

1. `AGENTS.md` 是**指令**，不是记忆。Codex 的记忆在 `~/.codex/memories_1.sqlite`（表 `stage1_outputs`，带 `usage_count` / `last_usage`），会话原文在 `sessions/**/rollout-*.jsonl.zst`；Claude Code 的记忆在 `~/.claude/projects/<project>/memory/`（`MEMORY.md` 索引 + 主题文件，frontmatter 带 `type` 与 `modified`）；Trae 的记忆是 `session_memory_*.jsonl`（`intent` / `actions` / `outcome` / `learned`）。策划书 §4.2 把 `AGENTS.md` 当作 Codex 的记忆来源，这个判断是错的。
2. 指令是**有序链**，不是单个文件。Codex 从 git root 往下走、越近越靠后覆盖前面的（并有 32 KiB 截断）；Claude 从 cwd 往上拼接、同目录 `CLAUDE.local.md` 排在后；Cursor 用 `globs` / `description` 条件加载。只存 `source_path` 表达不了"哪条生效"。
3. `source_kind` 的 `memory` 值太笼统，无法区分"工具自动写的记忆"与"从会话蒸馏的结构化记忆"。

**待定决策（三条，需分别点头）**：

| # | 建议 | 若不采纳的后果 |
|---|---|---|
| 1 | `source_kind` 扩展为 `instruction` / `auto_memory` / `session_distill` / `profile` / `doc`（`memory` 保留为兼容值） | 冲突裁决无法区分"指令冲突"与"记忆冲突"，`auto` 信任级的适用范围说不清 |
| 2 | `MemoryEntry` 增加 `precedence: int` 与 `layer: str`（`global` / `project` / `local` / `nested`） | Codex 的覆盖语义、Claude 的加载顺序在入库时丢失，事后无法还原 |
| 3 | 明确写入：**"Markdown 是唯一真相源"仅指输出侧（vault）**，输入侧允许 md / jsonl / zstd-jsonl / sqlite | P2-03 的接口会被"只解析 md"绑死，写第二遍是必然 |

**最终决策（2026-11-24，三条全部采纳）**：

| # | 结果 | 落地 |
|---|---|---|
| 1 | 采纳。`SOURCE_KINDS` 增加 `auto_memory` / `session_distill` / `profile`，`memory` / `transcript` 保留以兼容已有 vault | `models.py::SOURCE_KINDS` |
| 2 | 采纳。新增 `precedence: int = 0` 与 `layer: str = ""`（空值表示"该来源没有层级"，例如单文件记忆库） | `models.py`、`adapters/base.py::SourcePath` |
| 3 | 采纳。输出侧不变；输入侧由 adapter 自行决定解析方式，`Adapter.read()` 直接接收 `SourcePath` 而非文本 | `adapters/base.py` |

**第 3 条仍待所有者执行**：`AGENTS.md` 第 6 条「Markdown 是唯一真相源」需要加一句限定。契约文件由所有者维护，本 ADR 不代改。

**为什么这三条要一起拍**：它们共同决定 `MemoryEntry` 的字段集。分开改会连续破坏 `from_markdown` / `to_meta` 的稳定性，而字段语义是本项目明确要求"宁可不写功能也不要改"的东西。

**代价**：

- 采纳第 2 条要动 `models.py` 的字段集与 `_KNOWN_KEYS`，并补 `extra` 之外的兼容测试；已冻结的"字段已冻结"声明需要一份新的 ADR 修订。
- 第 3 条需要在 `AGENTS.md` 第 6 条上加一句限定，属于改契约文件，**只能由所有者动**。

**在拍板之前**：`models.py` 不动。适配器开发不启动（避免基于错的形状写两遍）。P2-01（PyYAML）可以照常做，它与此无关。

**采纳后的实际代价（已发生）**：`_KNOWN_KEYS` 与 `to_meta()` 各加两个字段，因此**已存在的 vault 条目在下次写入时会多出 `precedence: 0` / `layer: ''` 两行**。这是加性变更，旧文件仍可读；但 git diff 会出现一次性的噪音。

**复审时点**：P2-03 开工前必须拍板；`docs/04-upstream-formats.md` 每次上游大版本更新后复核。

## ADR-012 MCP 是分发的唯一通路，且第一阶段只读

**状态**：已采纳（2026-11-24）

**背景**：用户反复问"怎么把最新记忆分发给各个 AI 工具"。这个问题在 ADR-002 之后只剩一个诚实答案：**不推，让他们来拉**。

策划书原本的"中央库 → 各工具原生文件"写回已在 ADR-002 否决；`exports/` 目录保留但**没有任何代码写它**，这不是遗漏。于是"别的 AI 用上我的记忆"必须靠 MCP：AI 客户端主动查询，MemoryHub 只负责答对。

**决策**：

| # | 决策 | 理由 |
|---|---|---|
| 1 | **只读三件套** + **一个提案入口**：`memory_search` / `memory_get` / `memory_list` / `memory_propose`。**永不提供 `memory_write`** | 写能力一旦存在，ADR-002 与 ADR-003 都成了君子协定。`memory_propose` 只能产生 `status=pending`，是"交提案"而非"写库" |
| 1b | **提案必须过一道密钥形状检查**（`safety.py`）：命中即 `sensitivity=sensitive` → `blocked`，人不可批准 | 开放写入路径却不设防，等于让被提示注入的客户端把凭证明目张胆地存成 `auto` 可批的记忆。这不是检测器，只挡最容易挡的形状 |
| 2 | **可见性**：`search` / `list` 只返回 `status=approved` 且 `valid_until` 未过期的条目；`memory_get` 可返回任意状态，但响应里必须带 `status` 与 `trust` | 让未经人审的记忆流进别的 AI 的上下文，等于绕过 ADR-003。而按 id 查询是人的显式动作，允许并如实标注状态 |
| 3 | **每条结果必须带 provenance + validity**（`source_adapter` / `source_path` / `created_at` / `valid_until` / `superseded_by`） | 这是 MCP 相对"导出快照"的本质优势：快照一落地就开始过期且无人知晓，MCP 每次回答都能现算"这条还算数吗" |
| 4 | **只做 stdio 传输**，不做 HTTP | 本地工具，不需要端口、不需要认证、不暴露攻击面。`127.0.0.1` 的 HTTP 服务留到确有需要时 |
| 5 | 工具返回 **JSON 文本块**，不返回裸字符串 | 客户端（AI）需要能区分"事实"与"来源"，纯文本会把这层信息压扁 |

**理由**：`00-positioning.md` 的成功判据里有一条"能回答这条记忆为什么是这个值，且答案里带来源和时间"。**这条判据只有走 MCP 才可能成立**——写文件出去做不到，因为文件里没有裁决逻辑。

**代价（必须记住）**：引入 `mcp>=2.0`（实测 2.3.0），连带装进 `pydantic` / `anyio` / `httpx` / `starlette` / `uvicorn` / `sse-starlette` / `python-multipart` / `jsonschema`。其中 **`uvicorn` 与 `starlette` 只服务 HTTP 传输，本项目用不到**。这是当前第 2 个、也是依赖树最大的一次引入。

若将来打包体积或离线安装成为问题，可退化为**手写 stdio JSON-RPC**（MCP 的 stdio 子集只有 `initialize` / `tools/list` / `tools/call` / 通知，约 200 行，零依赖）。现在不这么做，是因为协议版本协商出错时，真实客户端会直接连不上，而 SDK 把这个风险降到零。

**复审时点**：P5-02（权限分级）时复审第 1、2 条；P6-01（PyInstaller 打包）时复审依赖树，届时再决定是否手写替换。

**追加（2026-11-24，同日）**：`memory_propose` 已落地。动因不是"想加功能"，而是一条外部事实——**Claude Desktop 的记忆在云端、本机读不到**（见 `04-upstream-formats.md` §3.0）。既然"采"这条路对云端工具不通，唯一能做的是让它们**自己把事实交过来**。这条也顺带把产品叙事从"我采集你"改成"你交给我、我裁决、大家来查"，后者在架构上更干净，也不受任何工具有没有本地文件影响。

权限分级（Read / Propose / Admin）仍未做：现在所有客户端都是 Propose 权限。`memory_write` 依然不存在。

## ADR-013 云端只有代码仓；用户记忆各自独立，且由机制而非约定隔离

**状态**：已采纳（2026-11-25）

**背景**：ADR-007 说了"代码与数据物理分离"，但它是一条散文规则。随后发生了两件事，证明散文挡不住人：

1. 提交 `479c23e` 把本机 WorkBuddy profile UUID 带进了 `docs/04-upstream-formats.md`；
2. 提交 `f5c59a4` 的**提交信息正文**里写了真实住址，而文件 diff 是干净的——只扫内容的检查完全看不到它；
3. 修完之后验证发现：**`force-push` 不等于删除**。GitHub 保留不可达对象，旧 SHA 仍可通过 `/commit/<sha>` 直接读到。历史改写只是让泄露"不容易找到"，不是"不存在"。

用户随后明确了产品边界：**云端那个仓只是项目开发仓；真实使用时，每个用户有自己的独立私有记忆仓**。这两件事必须分开实现，不能靠"记得别推错"。

**决策**：

| # | 决策 | 落点 |
|---|---|---|
| 1 | **云上只有一个仓，且只装代码。** 公开仓不含任何记忆正文、索引、日志、来源快照 | `git ls-files` 顶层只有 `src/ tests/ docs/ tools/` |
| 2 | **记忆仓由用户自己建、自己选远端。** MemoryHub 不代建、不代推、不代替用户决定托管在哪 | `init` 只 `git init`，不 `remote add` |
| 3 | **vault 不得位于任何 git 工作树内**（自身除外）。命中即拒绝初始化，无 `--force` | `boundary.violations()`，`init` 返回 2 |
| 4 | **vault 的远端不得指向代码仓**。`init` 写入 `pre-push` 钩子，命中即拒绝推送 | `boundary.PRE_PUSH_HOOK` |
| 5 | **提交信息视同发布内容**。内容扫描与信息扫描是两道独立门禁，缺一不可 | `tools/hooks/pre-commit` + `tools/hooks/commit-msg` |
| 6 | **`doctor` 把隔离当硬检查**：`repo isolation` 与 `vault remote` 任一不通过即 FAIL、退出码非 0 | `cmd_doctor` |

**理由**：

1. 三条边界（代码仓 / vault 工作副本 / vault 远端）对应三种泄露方式：提交、`git add -A`、推送。只防一种等于没防。
2. 门禁必须能在无人记得的情况下生效。`core.hooksPath=tools/hooks` 让钩子随仓库走，不依赖开发者本机配置。
3. 拒绝而不是警告：一旦 vault 落在代码仓内，第一次 `git add -A` 就把全部记忆写进公开历史，而**历史里的东西删不干净**（见背景第 3 条）。这个错误的代价不对称，所以按硬错误处理。

**代价**：

- clone 之后必须跑一次 `sh tools/setup_dev.sh`，否则钩子不生效（未启用时 `lint_staged.py` 仍可手动跑）。
- 测试夹具里刻意写成"像真的"的地址、手机号、密钥，要在该行加 `# pii:synthetic`，否则被自己的门禁拦下。
- `boundary` 用 `.git` 目录存在性判断仓库边界，不调用 git；bare 仓与 `GIT_DIR` 重定向场景未覆盖（当前不需要）。

**复审时点**：P5 加入远端同步能力时复审第 2、4 条——届时"用户自选远端"的默认值需要重新设计，但"代码仓永不接收记忆"不复审。

## ADR-014 条目粒度有上限，分类按内容不按来源

**状态**：已采纳（2026-11-25）

**背景**：首次导入 42 条真实记忆后实测：中位数 90 字，最短 9 字（`真实姓名绝不外泄`），最长 1276 字（整段项目清单）。同时 **42 条全部是 `profile`**，因为分类是适配器按来源硬编码的。

两个后果，都在真实使用里成立：

1. **审核失去意义。** 批一条 1276 字的条目等于一次批准二十件事，人只会点同意——这正是 ADR-003 想避免的。
2. **MCP 一条都查不到。** 可见性规则只返回 `approved`（ADR-012），而 42 条全是 `pending`。工具装完、导入完、别的 AI 拿到空结果，用户会以为坏了。

**决策**：

| # | 决策 | 落位 |
|---|---|---|
| 1 | **单条目上限 400 字**，超出按「子标题 → 空行段落 → 句子」三级回退切分 | `adapters/base.py: split_oversized()` |
| 2 | **父标题不下沉为空条目**，作为上下文并入首个子条目 | 同上 `_split_at_subheadings()` |
| 3 | **只有标题没有正文的条目直接丢弃** | `drop_heading_only()` |
| 4 | **分类按内容加权打分**，不按来源；权重 3 视为决定性（`github.com` / `绝不`） | `classify.py` |
| 5 | **`recategorize` 默认 dry-run**，逐条打印「原分类 → 新分类 + 命中词与权重」，`--apply` 才写 | `cli.py` |
| 6 | **`scan --refresh`** 把来源已不再产生的 pending 条目转为 `archived`（不删除），避免一次切分改动留两代条目 | `cli.py` |
| 7 | **`doctor` 报告 `mcp visibility`**：有条目但 0 条 approved 时报 WARN | `cli.py` |

**理由**：

1. 400 字来自实测分布：中位 90、P90 392。上限设在 P90 之上，只切真正过大的条目，不动本来合格的——**每次切分都会改变 id**，无谓切分等于制造噪声。
2. 加权而非先命中即赢：第一版把「## 当前重点项目 … 仓库 github.com/…」判成 `decision`，因为段里出现了一次"不得"。决定性权重让 `github.com` 一票定案，同段再多的"必须"也改不了结论。
3. dry-run 默认，因为改分类是改用户的归档判断，静默重写违背 ADR-009。
4. 归档而非删除：切分规则会继续演进，用户需要能回到上一代条目。

**实测结果**（`D:/my-memory`，2026-11-25）：

| 指标 | 迁移前 | 迁移后 |
|---|---|---|
| 条目数 | 42 | 59（53 pending + 6 archived） |
| 最长条目 | 1276 字 | 401 字 |
| 中位数 | 90 字 | 102 字 |
| `profile` 占比 | 100% | 40%（21/53） |
| 分类分布 | profile 42 | decision 21 / profile 21 / preference 10 / project 7 |

**代价**：

- 切分改变条目 id，已有审核结果无法自动迁移；本次是全 pending 状态下重导入，代价为零，将来在有 approved 条目时重扫需人工处理。
- 13 条命中不到任何规则，仍按导入时的 `profile` 落库；`recategorize` 会报出这个数字，但不猜。
- 规则表是中文关键词，换语言或换领域需重写；LLM 层（阶段 3）在此基础上叠加，不替换。

**复审时点**：阶段 3（LLM 分类）落地时复审第 4、5 条；规则误判率超过 20% 时复审权重表。

## ADR-015 规则分类实测 52.8%：AI 层从可选增强变为必需品

**状态**：部分采纳（2026-11-25）。审计方法与门禁已落地；三项设计变更待 owner 拍板，未定不改代码。

> **修订（同日）**：下面 52.8% 的数字**测错了**，原因是审计脚本把 `default=entry.category` 当兜底输入——那等于用被测量对象自己当尺子。vault 一旦审核入库，`entry.category` 就是人工标签，fallback 立刻"百发百中"：同一份代码同一天重跑，无信号命中率从 7.7% 跳到 84.6%。已改为固定常量 `DEFAULT_CATEGORY="profile"`。修订后整体 **54.7%（29/53）**、有信号 **70.0%（28/40）**、无信号仍是 **7.7%（1/13）**、project **25.0%（4/16）**。
>
> 结论方向不变（规则远低于可用线），但**教训比数字重要**：一个会随被测对象状态漂移的测量，比没有测量更危险，因为它看起来像证据。生产里 `recategorize` 仍用 `entry.category` 作兜底是对的（没信号的条目不该被挪走），错的是把这个行为带进审计。

**背景**：围绕「为什么用算法而不接 AI」，当时的结论是「算法作为 floor 站得住，AI 排在阶段 3」。这个结论**没有任何测量支撑**——ADR-014 自己写下「误判率超过 20% 时复审权重表」，却从未取过一次证。先把账补上，再谈取舍。

**已落地的部分**：

| # | 决策 | 落位 |
|---|---|---|
| 1 | 人工标注样本入库，只存 `id / 类别 / 错误类型`，**不存条目原文**（公开仓，避免 PII 回流） | `docs/audits/classify-labels-2026-11-25.tsv` |
| 2 | 审计脚本从私有 vault 实时读正文，输出整体/有信号/无信号三层准确率 + 混淆矩阵 | `tools/audit_classify.py` |
| 3 | `--min-accuracy` 不达标时退出码 1，可接 CI 作为回归门禁 | 同上 |
| 4 | `fallback` 由脚本按 reason 字符串独立判定，不信任人工标注；两者不一致时显式报告 | 同上 |

**实测结果**（53 条 pending，2026-11-25）：

| 指标 | 值 |
|---|---|
| 整体准确率 | 28/53 = **52.8%** |
| 有信号时 | 27/40 = 67.5% |
| 无信号（fallback）时 | 1/13 = **7.7%** |
| 按类别 | decision 73.3% / profile 64.3% / preference 57.1% / **project 23.5%** |

三项结论：

1. **fallback 是系统性误判，不是中性兜底。** 无信号时 7.7% 低于"恒猜 profile"的基线（26.4%），因为含"学校/专业/称呼"的 profile 条目本来就会命中关键词、进不了 fallback；能进来的恰恰是无词可依的 project 和 decision。静默返回 `default` 等于把 22.6% 的样本批量推向错误答案且不报错。
2. **project 类不可救。** 17 条真项目条目只认出 4 条。关键词手段在这个类别上不成立：真实项目条目（"某文明模拟，Android 上架"）不含"项目"二字；而"仓库/项目"在指令类文本里出现得更密。调权重救不回来。
3. **强词在长条目上过度支配。** `DECISIVE_WEIGHT=3` 修好了"先命中即赢"，代价是长段落里出现一次"绝不"就整条判为 decision。决定性权重只在短条目上是强证据。

**据此推翻的旧判断**：「算法够用、AI 可延后」。错在把"可解释"当成"够用"——可解释只解决错了能否看懂，不解决错多少次。

**待 owner 拍板（未定不改代码）**：

1. **fallback 显式化为 `unknown`**：无信号时不再返回 `default`，标记"需判定"强制进队列。改动最小，直接消掉 22.6% 的静默错误。建议无条件先做。
2. **AI 层前移，范围限定在 fallback + keyword 两类**（19 条 = 35.8%）：规则处理有把握的部分，AI 只处理规则自认没把握的部分，成本可控且每条可追溯是谁判的。
3. **先拆分再分类**：7 条 mixed 说明顺序反了。让 AI 先答"这段里有几个独立事实"，再逐条分类。

**代价**：

- 每一项都需要 API key 和网络；P3-01「无 API 时全部功能仍可用」的回归测试必须继续成立，AI 路径只能**补充**不能**替代**离线路径。
- 标注只有 53 条、单人、单库，且其中 7 条属"怎么标都说得通"。结论的外推范围仅限于此库；换语言、换领域要重新标。
- 类别体系本身有缺口：`knowledge` 在样本里零命中，长期职业路径类内容没有对应类别，被硬塞进 `profile`。这是体系问题，不是分类器问题，本 ADR 不解决。

**复审时点**：任一待拍板项落地后重跑审计，以 `--min-accuracy` 为准；若 AI 层加入后整体仍未过 85%，则问题在类别体系而非判定手段，届时复审 `CATEGORIES`。

## ADR-016 AI 层落地：算法找文件，AI 读内容，人审结论

**状态**：已采纳（2026-11-25）

**背景**：ADR-015 测出规则分类 52.8%，其中 `mixed`（一条含多主题）占 13.2%，`fallback` 占 22.6%。前者说明切分粒度错，后者说明关键词无覆盖。两者都是语义问题，加权重救不回来。

同时所有者提出一个更根本的质疑：**"直接读本地文件 → 用户接自己的 AI API → AI 汇总整理 → 存总库 → 其他 AI 读"，这条线为什么被做成了六步？**

**决策**：

| # | 决策 | 落位 |
|---|---|---|
| 1 | **职责三分**：`discover()` 仍是算法（找文件是确定的）；`read()` 在 AI 模式改走模型（语义）；写入必须人审 | `adapters/*.py` / `ai/organize.py` |
| 2 | **quote 定位校验**：每条提案必须带从原文逐字复制的片段，归一化（去空白/标点/大小写）后定位不到即标记待核实 | `ai/organize.py: quote_is_located()` |
| 3 | **不引入 Pydantic**：手写六字段校验，逐条丢弃、不整体失败 | `ai/schema.py` |
| 4 | **API key 只从环境变量读**，配置里只存变量名 | `ai/provider.py: api_key()` |
| 5 | **发送前明确告知且要求确认**：打印端点、模型、总字数，并声明「不做本地脱敏」；非交互环境需 `--yes` | `cli.py: _scan_with_ai()` |
| 6 | **CLI 收窄为主线六条**：`init` / `import` / `review` / `approve` / `mcp` / `doctor`，其余命令保留但移出帮助表（`review` 于 ADR-017 加入） | `cli.py: build_parser()` |
| 7 | **`config.save()` 支持 TOML 表，`init` 改为合并写入** | `config.py` / `cli.py: cmd_init()` |

**理由**：

1. **quote 是唯一能自动化的防幻觉手段。** 提示词可以要求"不许编造"，但只有"这句话在原文哪一段"能被机器验证。实测中编造的那条（原文并不存在的内容）被准确拦下并标记。
2. **不脱敏就直说。** 声明"已经脱敏"却实际发送原文，会让用户信任错误的东西；`safety.py` 的规则检测只用于入库分级，不能当发送前的过滤器用——它认不出语义型隐私。
3. **Pydantic 是反向依赖。** 为校验六个字段引入一个编译依赖，与 ADR-005 的取向相悖；手写校验还能给出逐条原因，比框架报错更可读。
4. **五条主线回应的是"复杂"的投诉，不是审美。** 20 个命令里真正构成产品的是这五条，其余是审核辅助与运维。`--help` 首屏只答"我该做什么"。
5. **修 `config.save()` 是先决条件，不是顺带。** 不修则用户手写的 `[ai]` 会被下一次 `init` 抹掉 —— 新功能自带一个必踩的坑。这是 HANDOFF 已知问题 #5，本次结清。

**代价**：

- 记忆内容会离开本机，且不经过任何本地脱敏。这是**用户显式选择接受**的代价，不是被隐藏的行为。
- 每次导入都要付费与等待；大文件按 24k 字一批切分，可能多次调用。
- 模型输出不稳定：同样的源，两次可能给出不同条数。因此 `quote` 校验与人工审核不能省。
- `import --ai` 与 `speed` 无关：53 条的真实库跑一次约需数十秒到数分钟，取决于端点。

**实测**：

- 213 个测试通过（新增 33 例：AI 层 27 + CLI 6）；`test_mcp` 因本机缺 `mcp` SDK 无法导入，属环境问题。
- 端到端：本地起 OpenAI 兼容假服务，真实 HTTP + 真实 CLI + 真实写库，4 条入库、分类正确、编造条目被标记待核实。

**未做（不要以为已有）**：

- 回写：仍不做，ADR-002 未推翻。所有者要的"其他 AI 更新同步各自记忆"需要"受管区块"方案（在入口文件中用标记包住生成内容，区块外永不触碰），本次未实现，见下方「未做」。
- 语义去重、冲突检测：P3-04 / P3-05 未开始。
- 摘要：`ai/organize.py` 只做拆分与分类，没有生成摘要字段。

**复审时点**：P3-04 落地后重跑 `tools/audit_classify.py`；若 AI 判定的未核实率持续高于 10%，问题在提示词而非模型，先改提示词。

## ADR-017 审核的队列可推导，游标不可推导

**状态**：已采纳（2026-11-25）

**背景**：ADR-016 完成后工具能整理、能检索，但 `D:/my-memory` 里 53 条全是 `pending`、`approved` 为 0，于是 MCP 对外恒为空。**功能齐全而无人使用**，瓶颈在最后一步：`approve` 要求先有 id，即「读列表 → 滚动 → 复制 32 位标识符」重复 53 次。每一步都是「改天再说」的合理理由。

**决策**：

| # | 决策 | 落位 |
|---|---|---|
| 1 | 待审队列**每次从 vault 重新推导**（`status=pending`），只有「跳过的 id」被持久化 | `review.py: build_queue()` / `ReviewState` |
| 2 | 跳过状态存 `~/.memoryhub/review.json`，**不进 vault** | `review.py: ReviewState` |
| 3 | 队列排序 = 未跳过组 + 已跳过组，组内按 `created_at` 再 id | `review.py: build_queue()` |
| 4 | 非 TTY 直接拒绝（exit 2）并指向 `approve <id>` | `cli.py: cmd_review()` |
| 5 | 单字母 + 回车，**不做 raw 单键**（POSIX 要 termios、Windows 要 msvcrt） | `review.py: ask()` |
| 6 | 改分类后**同一条重新显示**再决策；`blocked` 在界面层就禁掉 `a` | `review.py: run()` |

**理由**：

1. **可推导的东西存两份，就是给自己造一个能与真相冲突的东西。** 若把整条队列写进状态文件，删掉的记忆仍会出现在队列里、新导入的反而被跳过；这类 bug 不会报错，只会静默骗人。只存「跳过」是唯一不可从 vault 推导的部分。
2. **跳过必须被记住，否则 `s` 是假的。** 只是本轮排到队尾的话，下次运行它又回到第一个，用户会认为按键没生效。
3. **状态不进 vault，理由与 ADR-003 一致。** vault 里只应有记忆；cursor 文件会出现在 `git commit` 的 diff 里，也会成为「不是记忆」的第一个文件。放配置目录还能天然满足 ADR-013：它不在任何数据仓里。
4. **拒绝非 TTY，而不是「读到 EOF 就当结束」。** 后者会跑完 53 条、一条没决定、退出码 0 —— 看起来成功，实际什么都没做，这是最坏的一种失败。
5. **`blocked` 在界面层就禁掉 `a`。** `set_status` 里已有拦截，但让用户点一次再报错，等于用错误信息代替设计。

**代价**：

- 跳过清单可能无限增长。缓解：条目一旦被决定（批/拒）即从清单移除；`review --reset` 可整份清空。
- 游标不跨机器同步（它在本地配置目录）。多人多机审同一个 vault 时各自记住各自的跳过，这是可接受的，因为审核本来就是单人操作。
- 一屏一条意味着 53 条仍需 53 次按键。**这是有意的**：审核的成本应该体现在「读」上，而不是「操作」上。

**实测**：真实库只读校验 —— 53 条 pending、队列 53、无不可读文件；`tests/test_review.py` 22 例覆盖队列顺序、跳过持久化、断点续审、改分类、blocked 拦截、EOF、非 TTY 拒绝。

**复审时点**：若真实审核中出现「审到一半想回头改上一条」的抱怨，加 `u` 撤销上一步；若出现「想按分类快进」，那是 `--category` 过滤的事，不是游标的事。

## ADR-018 冲突检测只出提案，取代链只有一个写入口

**状态**：已采纳（2026-11-25）

**背景**：这不是设想出来的需求，是第一次真机接入时撞到的。库里同时有：

- `782bcbcf`（401 字）：「毕业论文（尚未冻结）：先确定题目 → …」
- `e6e751a1`（36 字）：「毕业论文：《基于多 Agent 架构的企业财务共享中心工作流程优化研究》」

两条都 `approved`、`valid_until=null`、`superseded_by=null`。Claude 会话按题面检索时读到了前者，答案与事实相反，而**库本身没有任何字段能判断谁覆盖谁**。这是目前唯一已经实际发生、用户可见的错误。

**决策**：

| # | 决策 | 理由 |
|---|---|---|
| 1 | 判定输入是**全部**已批准且未过期的条目，单次上限 300 条；超限**拒绝并提示 `--category`**，不静默截断 | 按相似度阈值先筛候选这条路已被实测否掉：上面那对条目在同分类 309 对里按字符 bigram 余弦只排 **31 名（0.052）**。阈值高到能排除噪音就必然漏掉这一对；而 50 条已批准正文合计约 8.5k 字，一次调用完全放得下 |
| 2 | 每条判定必须给出**两侧逐字引用**（各自条目内 6–40 字），归一化后定位不到 → 关系降级为 `contradicts` 并清空 `winner` | 与 ADR-016 同一条防线。区别是这里的代价更大：`organize` 里一条无据的条目只是多一条待审记忆，这里一条无据的判定会让人去归档一条真实记忆。**保留 pair、去掉判定**是唯一既不掩盖疑点也不制造结论的处理 |
| 3 | 提案写 `inbox/conflicts/*.json`，**不写 `.md`** | `VaultStore._readable_dirs()` 包含该目录并只 glob `*.md`。写成 Markdown 会让每条提案变成一个「读不出来的条目」：`doctor` 判 FAIL、`list` 告警，都是假警报 |
| 4 | 唯一写入口是 `memoryhub supersede <old> --by <new>`；**没有任何代码路径从模型输出直接写 `supersedes`** | ADR-002/ADR-003 的同一原则。模型能提案，能写库的只有人 |
| 5 | 四道闸：两个 id 必须存在；取代方必须 `approved` 且未过期；已被取代的不能再被取代；不许成环 | 第二道是关键：指向一条 `pending` 条目会把旧事实归档，而替代者对其他 AI 仍不可见 —— 事实从库里消失，比留着矛盾更糟。第一道补的是 HANDOFF 已知问题 #6（`supersedes` 无引用校验，可悬空） |
| 6 | 写入顺序：先给新条目加 `supersedes`，再给旧条目封窗 | 第二步失败时只是「新条目列了个还没退掉的前任」，可修；反过来会得到一条归档了却没人指向的记录 |
| 7 | 落实后提案移到 `logs/conflicts/` 并写入 `resolution`（保留 `keep`/`superseded`/`note`） | 「当时为什么退掉这条」是审计价值本身（ADR-006）。让它留在 `inbox/` 里又会让已处理的提案反复出现 |

**理由**：ADR-006 早就定义了 `valid_until` / `supersedes` 的语义和 `stamp_validity` 的写法，缺的一直是「谁来判断哪条该退」。补上这一层时，最容易被顺手做掉的是「AI 觉得该退就退」——那会让整条信任分级变成装饰。

**代价**：

- **一次检测 = 一次全量正文外发。** 所以 `--ai` 必须先确认（非 TTY 要显式 `--yes`），并明说「发送前不做脱敏」。这是隐私事件，不是开关。
- 语料超过 300 条后必须按 `--category` 分批跑；**跨批次的冲突会漏**，且脚本不会知道漏了。这是当前规模的取舍，不是可以忘掉的限制。
- 模型漏报时输出是「模型没有报告冲突」，而不是「库里没有矛盾」——文案刻意区分，因为后者是它无法知道的。
- 归档是整条生效的。像 `782bcbcf` 这种混装条目，退掉它就等于连带藏掉「工作台目录」「使用偏好」「管理文件」三件事。所以 `supersede` 在旧条目 >200 字或明显多段时额外警告，**正确的前置动作是先拆分**（P3-03 已有拆分能力），再取代。
- 提案与 `inbox/pending` 是两套东西：冲突提案不是记忆，不能 `approve`，也不会进 MCP。

**实测**：254 → 293 个测试（`tests/test_conflicts.py` 38 例），含一个真实 HTTP 端到端（本地假端点 → 校验 → 落提案 → 断言 vault 未被改动）。真实库只读验证：`conflicts` 空态给出 `--ai` 提示；`supersede --dry-run` 对上述真实条目正确打出「这条正文 401 字，可能不止一件事」的警告。

**2026-11-25 判定层重做（同一天，第二轮）：改成"块级 + 逐对"**

第一轮实测的结论是"机制对、判定层不可用"。重做后结论变了，但**只有在结构改变之后才变**。

| 改动 | 为什么必须这么改 |
|---|---|
| 比较单位从"条目"降到"片段"（`ai/claims.py`） | 400 字的汇总条目不是一件事，拿它当一件事比只能得出错答案。降粒度后，"汇总条目 vs 6 条独立记忆"不再产生 6 条"整条重复"，而是 6 条"某一句话重复" |
| 一次调用只判**一对**片段 | 稀释不是提示词问题。实测：只给那两条会报，加 6 条无关条目就返回空。**唯一可靠的解法是让无关条目物理上不在请求里**，不是求模型忽略它们 |
| 不再发送 `created_at` | 它是录入时间。第一轮的方向判反（让"晚录入的旧笔记"取代"已定题目"）就是这个字段造成的。提示词同时写死"只有措辞能证明先后" |
| 方向必须带证据，且证据要落在被判为较新的那一侧 | 与 quote 同一条防线。证不出来就降级为"矛盾、无方向"——说"两条冲突但不知道该信谁"比猜错方向有用 |
| 新增**主题锚点通道** | 这是最关键的一条，见下 |

**主题锚点通道是唯一能召回真实冲突的通道。** 实测数据：`毕业论文（尚未冻结）：先确定题目` 与 `毕业论文：《基于多 Agent 架构…研究》` 只共享 毕业/业论/论文 三个 bigram——恰好是语料里最常见的三个。按 IDF Dice 它排 **4,803 个片段对的第 207 名**，前面全是无害的近重复。但两条的**开头三个字完全相同**，而中文记忆就是"主题：内容"这么写的。加一条通道：开头三字相同的跨条目片段对全部纳入候选，且**不受 per_entry_pair 限制**（同主题就该逐句比完）。这条通道在真实库上产出 22 对，目标对排名从 207 升到 **18**。

**第二轮真实库实测（DeepSeek `deepseek-chat`，50 条 / 289 段）**：

```
切出 289 段可比较的内容
其中 4803 段对有共同用词，涉及 865 个条目对
未送审：35242 段对毫无共同用词；3340 段对因同一条目对过多被让位；1344 段对超出本次上限
本次送审 120 段对（其中 22 段因同一主题被保底纳入）
120 次调用，81,735 字发送 → 21 段对判为有关系，合并成 20 个条目对
```

产出 24 条提案：22 条"重复"、2 条"矛盾"，**全部 `verified=true`**（两侧引用都在对应片段里定位到）。两条"矛盾"正是那个真实用例——`e6e751a1`（已定题目）与 `782bcbcf`（尚未冻结）、`0fc37d5c`（已定题目）与 `782bcbcf`。抽查 5 条"重复"提案，全部是真重复（同一句话在两条记忆里各写一遍），且 `scope=partial` 正确标注"只涉及部分片段"。

**两个只有真实调用才会暴露的问题，已修**：

1. **"未定 vs 已定"被判成"不同层面"**。模型对目标对的第一次回答是 `none`，理由是"一个是题目、一个是选题流程的当前状态"。这不是幻觉，是规则缺口：提示词只写了"补充细节判 none"，没写"状态与结论是同一件事"。补上这条规则和正例后，同一对判为 `contradicts`，理由准确。
2. **`contradict` 少了复数 s 被判无效**。正确的判定因为一个字母被丢弃。加了别名表（`contradict` / `conflict` / `supersedes` 等）。**校验器造出来的假阴性，比宽松的校验器更糟。**

**仍未解决、且不可解决的**：4,803 个片段对里只送审 120 个（2.5%）。这是可观测的召回边界，不是"库里只有 24 个问题"。`stats` 里每个数字都给出来了，`--max-pairs` 可以扩大范围。**任何"没有冲突"的结论都只对送审的那批成立。**

**复审时点**：P3-04（语义去重）落地时。去重与冲突判定会争同一对条目的解释权 —— `duplicate` 是「同一件事的两份」，`supersedes` 是「同一件事的新旧两份」，合并方向必须由一个模块统一给，否则会出现「先合并再取代」和「先取代再合并」两条互斥路径。

**2026-11-25 真实模型实测：判定层不可用，别照着输出执行**

上面写着「已采纳」，但采纳的是**机制**，不是判定质量。当天接上真实端点跑了两次，结论必须记下来，否则下一个人会以为 `conflicts --ai` 的产出可以直接执行。

配置 DeepSeek（`deepseek-chat`，服务端实际路由到 `deepseek-flash`），50 条 8,541 字，1 次调用，7 秒，出 15 对（2 取代 / 13 重复）。三处硬伤：

1. **漏掉唯一那对真实冲突。** `782bcbcf` 与 `e6e751a1` 都在候选池、也在同一批 prompt 里，模型没报。A/B 实测：只给这两条时会报 `supersedes`，但 **winner 判反**（让「尚未冻结」取代「已定题目」，理由是「时间更晚」）；这两条加 6 条无关条目再问，直接返回 `{"pairs": []}`。**仅 8 条上下文就足以让这对消失**，所以本 ADR 第 1 条「全量一次送进模型」的前提在真实库上不成立。
2. **粒度错位。** `617c26b0` 一条被 6 条不同记忆判成「重复」。它是汇总条目（项目清单 + 兴趣 + 对外口径 + 提醒锚点 + 不推荐方向），每句话都能和某条独立记忆对上，模型就按「整条重复」报。照做 `supersede`，OMaster / SoundMesh / 摄影 / 兴趣会一起从检索里消失。
3. **时间语义错。** 模型用 `created_at` 判新旧。那是**录入时间**，不是事实发生时间：`782bcbcf` 是 11-25 才录入的旧工作台笔记，于是被判成「更新」。凡是「晚录入的旧事实」都会判反。

换 `deepseek-reasoner` 复跑：只报 3 对，**3 对全是同一类误报**（整条 vs 一句话），依然漏掉目标对。所以这不是换个模型能解决的事。

**结论与后续**：`ai/conflict.py` 的机制（提案不写库、两侧逐字引用、四道闸）保留且正确；**判定层标记为部分完成**，`conflicts --ai` 的产出只能当「值得人看一眼的线索」，不能照着跑 `supersede`。要修的是三件事：成对判定或小批判定（解决稀释）、提示词禁止把混装条目整条归档、禁止用 `created_at` 推新旧。这三条都属于重做判定层，不是调参。

顺带一个真缺陷：`max_tokens=8192` 喂 `deepseek-reasoner` 会返回空内容，而报错只说「模型返回了空内容」——思维链把配额吃满了。这条要在 `Provider._extract_text` 里按 `finish_reason=length` 给出明确提示。

## ADR-019 回写只写受管区块，读方必须剥掉它

**状态**：已采纳（2026-11-25）

**背景**：这个项目存在的理由是「三个 AI 各写各的记忆 → 一份真相 → 每个 AI 都读这一份」。前两步从阶段 1 就通了，第三步一直没做。没有第三步，「统一记忆」只是多了一个需要查看的地方。用户在 2026-11-25 明确要求补上：可以每条都人工审，也可以全自动，但最后必须能把结果送回去。

**决策**：

| # | 决策 | 理由 |
|---|---|---|
| 1 | ADR-002 不推翻，`Adapter.can_write` 仍恒为 `False`；回写是独立模块 `sync.py` | 两件事被混在一起过。adapter 的职责是**理解**别人的格式，让它去写就等于承诺能正确维护别人的文件——做不到。`sync` 做的是另一件事：在别人文件里追加一块自己负责的区域 |
| 2 | 只动 `<!-- MEMORYHUB:BEGIN -->` 与 `<!-- MEMORYHUB:END -->` 之间，区块外一个字节不碰；文件不存在时才创建 | 这是「可撤销」的唯一实现方式：删掉区块，文件与写之前逐字节相同。任何「顺手整理一下格式」都会让撤销变成不可能 |
| 3 | **读方必须先剥掉区块**（`managed.strip_block`），三个 adapter 全部照做 | 不剥就是自激循环：`sync` 写入 → `import` 采回 → 库里多一份自己的投影 → 下次 `sync` 写得更长。这个项目最该避免的就是「看起来在长记忆，其实在复制自己」 |
| 4 | 默认只出计划，`--write` 才落盘；写前备份 `*.bak-memoryhub-<时间戳>`，写后回读校验区块 | 这些是别的工具每次会话都要加载的文件。一条错误的命令只影响一次调用，一块错误的区块影响之后每一次会话 |
| 5 | 目标路径与 `adapters` 共用 `CLAUDE_HOME` / `CODEX_HOME` / `WORKBUDDY_HOME` | 读的地方和写的地方必须是同一处。两套路径最终会表现为「同步成功但什么也没发生」 |
| 6 | 所有目标收**同一份**内容，不按工具过滤 | 按工具裁剪听起来体贴，实际是把「两个 AI 说法不一致」重新引进来 |
| 7 | 只投影 `approved` 且未过期、未被取代的条目 | `pending` 是提案，`superseded` 是历史。把历史投给读者，等于让它拿旧事实回答新问题 |
| 8 | 不截断长条目；整块超过 40k 字只告警 | 截断让一条记忆的后半段在所有工具里消失，而且没人会发现。长是可观测的，丢是不可观测的 |
| 9 | 排序在 `render_block` 内部完成，不信任调用方给的顺序 | 区块顺序若随目录遍历变化，每次 `sync` 都会产生一个纯噪声 diff，人很快就会无视 diff |

**区块内容**：按分类分组（身份 / 决定与铁律 / 偏好 / 项目 / 事实），单行条目用列表项，多行条目保留自己的结构、首行加粗。多行不能塞进列表项——那些条目本身就是从 `##` 章节切出来的，再包一层列表会得到嵌套两层，markdown 直接变形。

**代价**：

- **重复是必然的。** vault 的内容本来就来自这些文件，写回去等于同一事实出现两次（原来是章节，现在是区块）。这是「给每个读者一份完整当前真相」的代价，不打算优化掉。
- **WorkBuddy 的 `MEMORY.md` 由它自己维护**，我们写的区块可能被它某次更新覆盖。区块丢了不影响 vault——vault 是唯一真源，重跑 `sync` 即可。反过来说，也不能把区块当存储用。
- **区块进上下文。** 真实库 50 条约 8.9k 字，`~/.claude/CLAUDE.md` 从 15KB 变成 35KB，每次会话多约一万 token。这是所有目标都收全量的直接后果，规模上去后需要 P5-02 的增量方案。
- 被取代的条目不会出现在区块里，所以**在分发侧看不到历史**。要看历史回 vault，`--include-expired`。
- 新建 `~/.codex/AGENTS.md` 会让 Codex 从此有一条它原来没有的指令。这是目标而不是副作用，但必须说清楚它发生了。

**实测**（2026-11-25）：313 个测试（`tests/test_sync.py` 20 例）全过。真实库写入三个目标后立刻跑 `import`：

```
claude     CLAUDE.md [global]: 0 new, 25 already present
workbuddy  MEMORY.md:          0 new, 17 already present
codex      AGENTS.md [global]: 0 new, 0 already present
entries    0 imported, 53 already present
```

区块内容一条也没被采回，待审队列仍是 1 条。这是本 ADR 第 3 条的唯一有效证据，也是 `EchoChamberTests` 存在的原因。

**复审时点**：P5-02（增量同步）——当区块大到影响会话成本时。届时也不能改成「只写变化」，因为每个读者需要的是完整当前状态，增量要求读者自己合并历史，没有哪个工具会做这件事。

## ADR-020 本地页面提前落地：队列没有表面就等于不存在

**状态**：已采纳（2026-11-25）

**背景**：同一天内 P3-05 在真实库上产出 24 条冲突提案，全部 `verified=true`、每条都带可定位的引文，然后**一条也没被处理**。原因不是判定质量，是消费方式：待审条目要在 TTY 里一屏一条地过（`review`），冲突提案是 `inbox/conflicts/*.json`，读它等于 `cat` 一堆 JSON。

roadmap 原本把 Web UI 排在阶段 6，门禁写的是「作者自用满一个月且仍想打开」。这条门禁是循环论证：**没有低摩擦入口，就不会长出「仍想打开」的习惯**，门禁因此永远不会满足。真正的判据应该是「积压是否在增长」——它在增长。

**决策**：

| # | 决策 | 理由 |
|---|---|---|
| 1 | 提前做 P6-03，范围只覆盖**两个队列**：待审 + 冲突提案 | 这两处是唯一「有产出、无表面」的地方。列表、检索、回写计划已经能从命令行一眼看完，为它们做界面是在解决不存在的问题 |
| 2 | 标准库 `http.server` + 单文件 HTML，零新依赖、无构建步骤 | 整个项目的依赖预算只有两个包（`pyyaml`、`mcp`）。为一个本地自用面板引入 npm/打包链，代价远大于收益 |
| 3 | 只绑 `127.0.0.1`，**不提供 `--host`**；`Host` 头必须是环回地址；每次启动一个随机 token，走自定义 header 而不是 cookie | 一个能批准记忆的页面不该被别的机器访问到。`Host` 校验防的是 DNS rebinding——外网站点可以把域名解析到 127.0.0.1 再让浏览器去请求，但它伪造不了 `Host`。用 header 而不是 cookie，则跨站请求天然不带凭证 |
| 4 | 页面是**视图**，不是第二套实现：写操作调 `store.set_status` / `conflicts.apply_supersede` | 取代链的四道闸和「`blocked` 硬拒绝」只写在一处。重写一遍规则，两条路径迟早会给出不同答案 |
| 5 | `sync --write` **留在命令行**，页面只展示计划 | 它改的是另外三个工具每次会话都要加载的文件。一次误点的影响不是一回，而是之后每一次会话 |
| 6 | `--read-only` 在**服务端**强制，不靠前端不发请求 | 前端的克制不是权限 |
| 7 | 长条目（≥180 字，或含 ≥3 个主题行）在取代前单独告警 | 真实库里唯一的真冲突是一条 401 字的「个人工作台」，混装目录、偏好、文件清单，其中只有一句论文状态过期。**按钮让错误动作比敲 id 更容易**，所以警告必须前置 |

**代价**：

- 多一个前台进程、一个端口、一份每次启动都失效的 token。它不常驻，关掉终端即结束。
- 「打开浏览器」从此成了一个有写权限的动作。这是这个 ADR 最需要被记住的一点。
- 只在 Windows x64 + Chrome/Edge 上验证过；Safari/Firefox 未测。
- 页面里的前端逻辑没有自动化测试，测试只覆盖 HTTP 层（鉴权、Host、四个写动作、提案序列化）。

**实测**（2026-11-25，真实库 `D:/my-memory`）：59 条（50 approved / 6 archived / 2 rejected / 1 pending）、24 条提案（20 duplicate / 4 contradicts）、25 个被提案涉及的条目里 13 条被判 crowded —— 包括那条 401 字的。`sync` 三个目标均「已是最新」。365 个测试全过（`tests/test_web.py` 20 例）。

**副产品（真实 bug）**：做页面需要分类标签，才发现 `sync.CATEGORY_ORDER` 里写的是 `fact`，而模型层的分类是 `knowledge`。后果不是报错，而是**所有 knowledge 条目被排到回写区块的尾部、标题显示英文 `knowledge`**——三个 AI 读到的每一份区块都受影响，没有任何测试发现它，因为它不崩。已修，并加了「顺序表必须是 `models.CATEGORIES` 的排列」的测试。这是「先做表面」的意外收益：界面逼你逐个念出字段名。

**复审时点**：当页面开始需要「编辑正文」或「全库检索」时。那时应该先问是不是该直接把 vault 当 Obsidian 库打开，而不是再往这个页面里加功能——它存在的唯一理由是那两个队列。
