## 1. 项目概述与立项动机

### 1.1 项目概述

MemoryHub 是一个本地优先的跨 AI 记忆管理工具。它运行在用户自己的电脑上，连接不同 AI 编程助手和 Agent 的本地记忆、规则文件或用户指定的上下文文件，将变化收集到统一记忆库；在需要时调用用户配置的 AI API，对记忆进行分类、去重、合并、冲突识别和压缩；经过用户审核后，再将标准化结果分发给不同 AI 工具，并通过 GitHub 私有仓库进行版本备份。

产品不是另一个聊天机器人，也不是要求所有 AI 使用同一种内部记忆实现。它提供的是一个跨工具的记忆管理层和适配层。

### 1.2 为什么要做这个工具

用户在日常工作中会同时使用多个 AI 工具，例如 Codex、Claude Code、Cursor 以及其他本地或云端 Agent。每个工具可能拥有自己的记忆文件、项目规则、上下文管理机制或独立配置。随着使用时间增长，用户偏好、项目背景、技术决策和长期任务会分散在不同工具中。

记忆分散：不同工具分别积累上下文，用户需要重复解释背景、偏好和项目情况。

内容重复或冲突：不同工具可能保存相同信息的不同版本，甚至保留已经过时的结论。

迁移成本高：更换工具或新增 Agent 时，原有记忆难以完整迁移。

缺少统一治理：用户很难知道哪些记忆来自哪里、何时产生、是否过期、是否经过确认。

备份与回滚不足：单个工具的记忆通常不是用户可统一管理的长期资产，误修改后恢复也不方便。

隐私与控制权：把记忆交给某个云服务并不一定符合用户对本地数据、API 选择和可迁移性的要求。

### 1.3 核心问题定义

> 核心问题 用户拥有多个 AI 工具，却没有一个独立于具体厂商、可审查、可迁移、可备份的个人记忆管理层。

因此，产品要解决的不是“让一个 memory.md 文件被所有 AI 读取”这么简单，而是建立一套统一记忆格式、工具连接器、审核机制、同步状态管理和备份机制。

### 1.4 产品目标

| 目标 | 说明 | V0.1 衡量方式 |
|---|---|---|
| 统一管理 | 把多来源记忆收集到中央记忆库 | 至少完成 Codex、Claude Code 两类来源的文件导入 |
| 保持原有工具习惯 | 不强制用户迁移或关闭原生记忆 | 原始来源只读采集，分发写入授权目标 |
| 可信整理 | 支持 AI 辅助去重、分类、冲突分析 | AI 输出先进入待审核区，未经批准不写正式库 |
| 实时感知 | 文件变化后尽快发现并处理 | 事件触发 + 防抖 + 哈希去重 + 周期扫描校准 |
| 可迁移与可恢复 | 使用开放文件格式和 Git 版本管理 | 删除索引数据库后可重建；可从 Git 恢复正文 |
| 本地优先 | 不依赖自建服务器或强制云账户 | 核心功能在本机运行，AI API 可选 |

### 1.5 非目标

不训练或托管自己的大语言模型。

不在 V0.1 建立云端账户体系、中心化 SaaS 服务或自建同步服务器。

不承诺所有 AI 工具都能自动双向同步；适配能力取决于工具开放的文件和接口。

不将 GitHub 当作本机实时同步总线或多人协同数据库。

不默认把整个用户记忆目录上传给云端模型。

## 2. 问题分析与目标用户

### 2.1 目标用户

| 用户群体 | 主要痛点 | 产品价值 |
|---|---|---|
| 多 AI 工具重度用户 | 跨工具重复交代背景，偏好与项目记忆分散 | 统一记忆管理与跨工具分发 |
| AI 编程用户 | 项目规则、开发约定和技术决策分布在不同仓库与 Agent 中 | 维护可迁移的开发上下文 |
| 个人 Agent / 自动化开发者 | 多个 Agent 缺少共享的长期用户上下文 | 通过 MCP、CLI 和文件接口复用记忆 |
| 重视隐私的本地优先用户 | 不希望依赖单一云端记忆服务 | 本地存储、用户自选 API、Git 私有备份 |

### 2.2 典型使用场景

用户在 Claude Code 中补充一条项目决策，MemoryHub 监测到文件变化，将其作为新来源记录。

用户在 Codex 中更新了个人开发偏好，系统识别到中央库存在相近但较旧的记录，生成合并建议。

AI 发现两条记忆相互矛盾时，展示来源、时间和差异，由用户决定保留哪条或改写。

用户批准一条记忆后，系统更新中央库，并生成 Codex / Claude Code 可读取的适配文件。

用户离开电脑或定时任务运行时，系统将正式记忆提交到本地 Git，并推送至用户配置的 GitHub 私有仓库。

### 2.3 产品价值主张

> 产品主张 Your AI. Your Memory. Your Rules. —— AI 可以共享记忆，但记忆的所有权、审核权和迁移权属于用户。

## 3. 产品定位、价值与设计原则

### 3.1 产品定位

定位为 Local AI Memory Infrastructure（本地 AI 记忆基础设施），而不是单一 MCP Server、单一记忆文件编辑器或云端知识库。

### 3.2 三类同步关系

| 方向 | 职责 | 规则 |
|---|---|---|
| 外部 AI 工具 → 中央库 | 采集（Import） | 读取原始记忆、记录来源与哈希，不直接覆盖中央正式记忆 |
| 中央库内部 | 整理（Consolidate） | 规则与可选 AI 分析；生成差异、重复和冲突建议；审核后写入 |
| 中央库 → 外部工具 / GitHub | 分发与备份（Export / Backup） | 按目标工具格式生成文件；Git 版本化并推送远端 |

### 3.3 设计原则

本地优先：用户数据默认留在本机，联网仅用于用户明确配置的模型 API 和 Git 远端。

混合记忆：不替换各 AI 工具原有记忆机制，中央库作为统一治理层。

单一真实数据源：中央 Markdown Vault 是正式记忆正文的唯一真相源。

可逆操作：AI 整理先提案，正式写入可追踪、可回滚。

适配器隔离：不同工具的文件结构差异由 Adapter 处理，不污染核心数据模型。

渐进兼容：优先支持本地可读写文件的工具，再扩展 MCP、HTTP API 和 SDK。

最小权限：默认只读采集；只向用户明确授权的目标文件写入导出内容。

无 AI 也能工作：AI 增强体验，但不成为基础数据管理的强制依赖。

## 4. 相关资料与技术依据

本项目依赖的技术大多已有公开规范或成熟实现。下表列出适合开发前阅读的官方资料。产品对具体 AI 工具的适配方式仍需在实际版本上验证，不能仅凭文件名推断其内部记忆机制。

| 资料 / 项目 | 与本项目的关系 | 策划阶段结论 |
|---|---|---|
| Model Context Protocol（MCP）规范 | 为 AI 客户端连接本地记忆服务提供标准工具接口 | V0.1 优先支持 stdio；Streamable HTTP 后续增加 |
| Codex AGENTS.md 文档 | 说明 Codex 如何读取全局和项目级指令文件 | 可作为上下文来源和导出目标之一，但不等同于 Codex 内部全部记忆 |
| Claude Code Memory 文档 | 用于核实 Claude Code 自动记忆和文件组织方式 | 适配器需检测实际目录、权限和版本，避免假设所有用户路径相同 |
| Watchdog 文档 | 跨平台监听文件系统事件 | 用于实时变化感知；仍需定期全量/增量扫描补偿丢失事件 |
| SQLite FTS5 文档 | 提供本地全文搜索索引 | 可用于中央记忆搜索，索引可从 Markdown 重建 |
| Git 官方文档 | 提供本地版本历史、提交、远端推送与恢复 | 适合作为备份与回滚工具，不适合作为实时协同数据库 |
| Pydantic 文档 | 验证结构化数据和 AI 返回结果 | 用于约束模型输出，拒绝不合规提案 |

### 4.1 MCP：连接层，而不是记忆数据库

MCP 负责定义客户端与服务端之间的工具调用和消息传输，不负责替用户决定记忆如何存储、审核或同步。当前标准传输包括 stdio 与 Streamable HTTP；stdio 模式由客户端启动本地子进程，通过标准输入输出交换消息。协议要求 stdout 只输出 MCP 消息，因此日志应写入 stderr。

V0.1 采用 MCP stdio 的原因是配置相对简单、不需要开放本地网络端口，适合 Codex 等本地客户端。多个客户端可各自启动 MCP 子进程，但所有进程必须通过同一个 Core API、文件锁和原子写入策略访问中央库。

### 4.2 Codex / Claude 等工具的适配边界

Codex 的 AGENTS.md 是持久指令和项目上下文机制，不应直接等同于通用个人记忆数据库。Claude Code 的记忆文件与主题组织方式也可能随版本和用户设置变化。适配器应采用“自动发现 + 用户确认路径 + 只读扫描 + 能力声明”的方式，不能将未验证的路径或写入能力写死。

### 4.3 文件监控不是绝对可靠的事件总线

Watchdog 能在 Windows、macOS、Linux 等平台抽象文件系统事件，但底层事件行为存在平台差异，监控缓冲区也可能发生事件丢失。因此实时同步必须采用“文件事件触发 + 防抖 + 哈希核验 + 周期性扫描校准”的组合策略。

### 4.4 Git 的正确定位

Git 负责本地历史版本、差异查看、提交和远端推送。它适合备份和跨设备获取历史版本，但不应被当作本机多个 AI 进程之间的实时消息系统。不同设备同时修改同一记忆文件时，仍需要拉取、合并和冲突处理。

## 5. 总体架构设计

### 5.1 架构总览

```text
┌──────────────────────────────────────────────────────────┐
│                   外部 AI 工具 / Agent                    │
│       Codex        Claude Code        Cursor        Other │
└───────────────┬───────────────┬───────────────┬──────────┘
                │ 文件 / MCP / CLI / 用户授权目录
                ▼
┌──────────────────────────────────────────────────────────┐
│                  Connector / Adapter Layer               │
│   发现路径 · 读取解析 · 文件监控 · 哈希 · 能力声明        │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌──────────────────────────────────────────────────────────┐
│                      Memory Core                          │
│  Import  ·  Normalize  ·  Deduplicate  ·  Conflict Check  │
│  Proposal  ·  Approval  ·  Export  ·  Version Control     │
└──────────────┬──────────────────────────────┬────────────┘
               ▼                              ▼
┌──────────────────────────┐     ┌──────────────────────────┐
│ Canonical Markdown Vault │     │ SQLite State / FTS Index│
│ 正式记忆正文唯一真实来源 │     │ 可重建索引、任务和哈希   │
└──────────────┬───────────┘     └──────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────┐
│ AI Processor (Optional) + Approval Manager               │
│ 分类 · 摘要 · 语义去重 · 冲突建议 · 变更差异 · 人工审核   │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌──────────────────────────────────────────────────────────┐
│ Distribution & Backup                                    │
│ 目标工具专属文件 / MCP 读取 / 本地 Git / GitHub Private  │
└──────────────────────────────────────────────────────────┘
```

### 5.2 核心模块职责

| 模块 | 职责 | 关键约束 |
|---|---|---|
| Connector Layer | 发现、读取和监控外部工具的记忆来源 | 默认只读；来源路径由用户确认；不假设所有格式一致 |
| Memory Core | 统一解析、去重、冲突检测、提案和正式写入 | 所有写操作经过核心层；原子写入与锁 |
| Canonical Vault | 保存正式记忆正文 | Markdown + YAML 元数据；可由 Git 版本化 |
| SQLite State DB | 索引、来源快照哈希、任务状态、同步状态 | 不是正文真相源；可重建 |
| AI Processor | 语义理解、分类、摘要和冲突建议 | API 可选；结构化输出；不直接写正式库 |
| Approval Manager | 审核、编辑、拒绝、回滚 | 默认人工确认；保留操作记录 |
| Distribution Engine | 将中央记忆转换成目标工具格式 | 只写入授权的导出位置；避免覆盖原生数据 |
| Git Manager | 本地提交、远端推送、拉取和冲突提示 | 正式内容优先；敏感文件排除；不自动强制覆盖 |

### 5.3 单进程核心与多接口

建议采用一个本地 Core Engine，外部通过不同接口调用它。CLI、MCP stdio 和本地 Web UI 不应分别实现自己的记忆逻辑。所有操作统一进入 Core API，确保权限、校验、锁、审核和日志行为一致。

| 接口 | V0.1 状态 | 用途 |
|---|---|---|
| CLI | 必须 | 初始化、诊断、导入、审核、备份、同步 |
| MCP stdio | 必须 | 本地 AI 客户端读取、搜索和提交记忆提案 |
| 本地 Web UI | 基础版 | 状态查看、待审核列表、配置和差异预览 |
| Streamable HTTP | 暂缓 | 为多个本地客户端提供常驻服务 |
| SDK（Python / Node） | 暂缓 | 第三方开发者集成 |

## 6. 记忆数据标准与目录规范

### 6.1 为什么不只用一个 memory.md

单个 memory.md 容易随着使用时间变得过长，难以分类、更新和分发。V0.1 建议采用多个 Markdown 文件构成 Vault，按个人资料、偏好、项目、知识和决策分类。对用户而言仍然是普通文件；对程序而言则通过元数据和索引管理。

```text
MemoryHub/
├── vault/
│   ├── profile.md
│   ├── preferences.md
│   ├── projects/
│   │   ├── project-a.md
│   │   └── project-b.md
│   ├── knowledge/
│   └── decisions/
├── sources/
│   ├── codex/
│   └── claude/
├── inbox/
│   ├── pending/
│   ├── conflicts/
│   └── rejected/
├── exports/
│   ├── codex/
│   └── claude/
├── config/
├── database/
│   └── index.db
├── logs/
├── .gitignore
└── manifest.yaml
```

### 6.2 统一记忆条目

每条记忆建议具有稳定 ID 和明确来源。正文保持人类可读，元数据采用 YAML Frontmatter 或单独的结构化索引。下列字段是 V0.1 的建议基线，后续可演进。

> --- id: mem_000001 category: preference source: - adapter: codex path: "user-memory/preferences.md" created_at: "2026-11-23T10:00:00+08:00" updated_at: "2026-11-23T10:00:00+08:00" status: approved confidence: high sensitivity: normal tags: - development --- 用户开发项目时优先考虑 Python； 除非存在明确性能需求，否则不优先选择 Rust。

| 字段 | 含义 | 要求 |
|---|---|---|
| id | 记忆唯一标识 | 生成后保持稳定，不因移动文件而改变 |
| category | 记忆分类 | 如 profile / preference / project / knowledge / decision |
| source | 原始来源 | 记录工具、路径或导入来源 |
| created_at / updated_at | 时间信息 | 使用明确时区的 ISO 8601 |
| status | 审核状态 | pending / approved / rejected / archived |
| confidence | 可信程度 | 可选，不能把模型自评当成事实 |
| sensitivity | 敏感级别 | normal / personal / sensitive / secret |
| tags | 标签 | 用于筛选和适配导出 |

### 6.3 数据分层

| 层级 | 内容 | 是否进入正式库 / Git |
|---|---|---|
| Raw Source Snapshot | 从外部工具读取的原始快照或必要摘录 | 默认不进入 Git；按隐私策略配置 |
| Pending Proposal | 待整理、待审核的提案 | 默认不推送 GitHub |
| Canonical Memory | 用户确认后的正式记忆 | 可进入 Git，但必须先做敏感信息过滤 |
| Export Artifact | 针对某个 AI 工具生成的文件 | 原则上可重建；默认不作为唯一真相源 |
| Runtime State | 哈希、任务状态、索引、日志 | 不进入 Git |

## 7. 核心业务流程与同步机制

### 7.1 实时变化处理

文件监控器发现来源文件新增、修改、删除或重命名事件。

事件进入队列，进行 2–5 秒防抖；同一文件短时间内的多次事件合并处理。

读取文件并计算 SHA-256；若哈希与上次快照一致则忽略。

适配器解析文件，保留原始路径、工具类型和时间信息。

先进行规则级过滤、完全重复检测和敏感信息检测。

如启用 AI API，则批量生成标准化提案、语义重复和冲突分析；否则生成基础导入提案。

提案进入待审核区；用户批准后更新正式 Markdown。

分发器按目标工具模板生成导出文件，记录版本和内容哈希。

Git Manager 对已批准的正式变更提交本地版本，并按策略推送远端。

### 7.2 为什么必须有周期性校准

文件系统事件是实时感知手段，不应作为唯一正确性来源。监控程序重启、系统休眠、缓冲区溢出、网络盘行为或权限变化都可能导致漏报。因此需要每隔一段时间对已配置来源做轻量扫描，以文件哈希补齐遗漏事件。

| 机制 | 建议初始值 | 目的 |
|---|---|---|
| 文件事件防抖 | 2–5 秒 | 等待编辑器完成写入，合并连续事件 |
| 轻量状态校准 | 每 5–15 分钟 | 检测漏掉的变更 |
| GitHub 推送 | 每 30 分钟检查一次 | 有新提交才推送 |
| AI 批处理 | 按事件队列聚合 | 减少 API 调用和费用 |
| 失败重试 | 指数退避，有限次数 | 避免网络错误导致任务风暴 |

### 7.3 防止同步循环

分发到目标工具的文件也可能被文件监控器发现。系统必须通过来源标记、目标路径排除规则和内容哈希识别自身写入，避免把自己的导出结果重新导入，造成循环、重复和版本震荡。

> source: memoryhub target: codex memory_version: 12 content_hash: "sha256:..." exported_at: "2026-11-23T22:00:00+08:00"

### 7.4 冲突处理原则

不同来源内容相同：合并来源引用，不重复生成多条记忆。

内容相近但表达不同：可提出合并建议，保留原始来源。

内容直接矛盾：不自动选择；展示时间、来源和差异，交由用户判断。

新旧信息冲突：时间只作为证据之一，不能简单认定最新内容必然正确。

用户明确修正：可将其标记为高优先级用户确认事实，并记录修订历史。

### 7.5 实时同步的能力边界

> 重要定义 V0.1 的“实时”指本地文件变化能够被尽快发现并进入处理队列，不代表所有 AI 客户端的内部上下文缓存会立即刷新，也不代表云端 AI 网页能够直接访问用户电脑。

### 9.2 Windows 首发形态

核心进程：MemoryHub Core，负责文件监控、任务队列、索引和同步。

本地 Web UI：绑定 127.0.0.1，仅用于本机配置、审核和状态查看。

系统托盘：可放在后续小版本，显示运行状态、待审核数量和同步异常。

### 9.3 本地服务与远程 AI 的差异

本地 AI 客户端可以通过 MCP stdio 或本地文件访问本机记忆；云端网页 AI 通常运行在远程环境，不会因为用户电脑安装了 MemoryHub 就自动获得本地磁盘访问权限。后续若要支持云端客户端，需要使用受支持的远程 MCP 接入方式、用户明确授权的连接器或受控同步服务。这不属于 V0.1 的承诺范围。

### 10.2 并发与写入一致性

所有正式写入集中经过 Memory Core，不能由多个 Adapter 各自写入 Vault。

写文件采用临时文件 + 原子替换；跨进程写入使用文件锁或 SQLite 事务协调。

同一条记忆通过稳定 ID 管理；文件路径变化不能改变 ID。

每次修改记录版本、来源、时间和变更摘要。

索引更新失败时可从 Markdown 重建，不应导致正式记忆丢失。

## 11. 安全、隐私与可靠性设计

### 11.1 数据隐私

默认本地存储；不配置 AI API 时不向外部模型发送内容。

调用云端 AI 前显示数据范围、敏感信息过滤结果和目标 Provider。

支持排除目录、文件名模式和内容规则。

API Key 不写入 Markdown、Git 仓库或普通日志；使用系统凭据存储或受保护配置。

GitHub 仓库默认 Private；Private 不等于加密，敏感信息仍必须在提交前过滤。

原始来源快照和待审核内容默认不自动推送远端。

### 11.2 AI 输入安全

来自外部记忆文件的文本应视为不可信数据，而不是系统指令。恶意或异常内容不能改变 MemoryHub 的审核策略、权限边界或密钥处理规则。模型输出必须经过 schema 校验、路径白名单检查、敏感信息检测和差异审核。

### 11.3 本地 HTTP 安全

只绑定 127.0.0.1，不默认监听 0.0.0.0。

校验 Origin，配置本地认证令牌，限制跨站请求。

按接口实施 Read / Propose / Admin 权限；默认不给直接写入权限。

避免暴露任意文件读取、任意路径写入和任意命令执行接口。

### 11.4 可靠性与恢复

文件事件丢失后通过周期性扫描恢复发现。

导入和导出记录哈希，重复事件不重复写入。

Git 操作失败不影响本地 Vault；远端不可用时保留本地提交。

数据库损坏可删除并重建；Markdown Vault 可独立读取。

提供导出 ZIP / Git clone / 从指定 commit 恢复等恢复路径。

## 12. V0.1 开发计划与验收标准

### 12.1 开发阶段

| 阶段 | 主要工作 | 阶段验收 |
|---|---|---|
| 阶段 1：核心数据层 | Vault 初始化、Markdown 规范、元数据、CRUD、搜索、原子写入 | 不连接 AI 也能管理记忆；删除 SQLite 后可重建 |
| 阶段 2：来源采集 | Codex / Claude 路径配置、解析、文件监控、哈希和周期扫描 | 来源变更可被发现并形成导入记录 |
| 阶段 3：AI 整理 | Provider 配置、结构化输出、分类、去重、冲突建议 | AI 只生成提案，不直接修改正式库 |
| 阶段 4：审核系统 | 待审核列表、差异对比、批准/拒绝/编辑、历史记录 | 未经批准内容无法进入正式记忆 |
| 阶段 5：分发与备份 | Codex / Claude 导出、Git commit / push、失败重试 | 导出可识别来源；Git 可恢复正式记忆 |
| 阶段 6：产品化 | 后台常驻、基础 UI、开机启动、Doctor、安装包和文档 | 普通用户可完成安装、配置、审核和备份 |

### 12.2 V0.1 验收用例

| 测试 | 预期结果 |
|---|---|
| 修改已配置的 Claude 来源文件 | 监控器在防抖后发现变化并记录新哈希 |
| 修改 Codex 来源文件 | 适配器识别变化并生成待处理条目 |
| 两个来源包含相互矛盾内容 | 生成冲突建议，不自动覆盖正式记忆 |
| 未配置 AI API | 基础导入、规则去重、审核、导出和 Git 仍可用 |
| AI 返回格式错误 | Pydantic 校验失败，提案被拒绝或要求重试 |
| 用户拒绝一条提案 | 保留拒绝记录，不在下一轮无条件重复导入 |
| 导出文件触发监控器 | 系统识别为自身输出，不形成循环导入 |
| GitHub 网络不可用 | 本地 Vault 和本地 commit 正常；远端任务进入重试状态 |
| 删除 SQLite 数据库 | 可从 Markdown 和配置重建索引与来源状态 |
| 恢复 Git 历史版本 | 可恢复中央正式记忆，且能查看差异 |

### 12.3 建议开发顺序

采用小步迭代：先完成核心数据模型与文件读写测试，再开发一个来源适配器，验证采集与审核闭环后再扩展第二个适配器。不要一开始同时开发所有工具适配、AI Provider、MCP、HTTP 服务和完整 UI。

首个可演示闭环建议为：导入一个来源文件 → 生成标准记忆提案 → 人工批准 → 写入中央 Markdown → 导出一个目标文件 → 本地 Git commit。

## 13. 风险、限制与待决策事项

| 风险 / 限制 | 可能影响 | 应对方案 |
|---|---|---|
| 工具记忆机制不开放或版本变化 | 无法稳定自动读取或写入 | 用户选择路径；适配器版本检测；只承诺已验证能力 |
| 云端 AI 无法访问本机文件 | 无法直接实时采集云端对话记忆 | 通过本地客户端、MCP、用户导出或受支持连接器接入 |
| 文件事件漏报 | 同步不完整 | 周期扫描校准、哈希对比和事件丢失恢复 |
| 自动合并错误 | 长期记忆被污染 | 冲突不自动决策；人工审核；版本回滚 |
| 同步循环 | 重复导入、反复覆盖 | 来源标记、目标排除、内容哈希和任务幂等键 |
| 隐私数据泄漏 | 敏感记忆上传模型或 GitHub | 本地过滤、脱敏预览、敏感信息阻断和加密备份选项 |
| 多进程并发写入 | 文件损坏或数据覆盖 | 单一 Core API、原子写入、锁和事务 |
| 多设备同时修改 | Git 冲突和状态分叉 | V0.1 只做备份；后续单独设计多设备同步协议 |
| 中文全文搜索效果 | FTS 默认 tokenizer 可能不理想 | 验证中文分词；评估自定义 tokenizer 或替代搜索方案 |

各适配器是否可安全写入专用导出文件，以及工具读取这些文件的优先级。

## 附录 A：术语表

| 术语 | 解释 |
|---|---|
| Canonical Memory | 中央标准记忆库；正式记忆的唯一真实数据源 |
| Adapter / Connector | 面向某个 AI 工具或来源的连接器，负责发现、读取、解析和导出 |
| Import | 将外部记忆读取到系统并保留来源 |
| Consolidation | 对多个来源记忆进行分类、去重、合并、冲突分析和压缩 |
| Proposal | 待审核的记忆变更建议 |
| Export / Distribution | 把中央记忆转换成目标 AI 工具可读取的格式 |
| MCP | Model Context Protocol，用于 AI 客户端与工具服务之间的标准化交互 |
| FTS5 | SQLite 的全文检索扩展 |
| Debounce | 防抖；将短时间内连续文件事件合并处理 |
| Idempotency | 幂等；同一事件重复执行不会产生重复结果 |
| Source of Truth | 唯一可信数据来源；本项目中指中央 Markdown Vault |
