# 分类规则实测报告（2026-11-25）

被测对象：`src/memoryhub/classify.py`（加权关键词分类）
样本：`D:/my-memory` 中全部 53 条 `pending` 条目
标注：`docs/audits/classify-labels-2026-11-25.tsv`（公开仓，只含 `id / 类别 / 错误类型`，不含条目原文）
复现：`python tools/audit_classify.py --vault D:/my-memory --min-accuracy 0.85`

## 结论

**规则整体准确率 52.8%，远低于可用线。** `docs/01-decisions.md` 里写下的复审条件是「规则误判率超过 20% 时复审权重表」——实测误判率 **47.2%**，条件已被触发。

此前"算法够用、AI 层可以放到阶段 3"是判断，不是结论。现在它有数据了，而这个判断是错的。

## 一、总体指标

| 指标 | 值 | 说明 |
|---|---|---|
| 整体准确率 | **28/53 = 52.8%** | 含 fallback 蒙对的 1 条 |
| 有信号时 | **27/40 = 67.5%** | 真正由规则做出的判断 |
| 无信号时 | **1/13 = 7.7%** | 无关键词命中，回落 `default` |
| fallback 触发率 | 13/53 = 24.5% | 四分之一的条目规则一个字都没匹配上 |
| 错误总数 | 25 条 = 47.2% | |

「有信号 / 无信号」必须分开看。规则不命中时返回调用方的 `default`（实为 `profile`），这条路径**没有做出判断**，却会算进准确率。把它拎出来之后，两个数含义完全不同：规则在有词可依时能到 67.5%，无词可依时是 **7.7%**——比"恒猜 profile"（样本中 profile 占 26.4%）还低。

## 二、按类别拆开，问题集中在 project

| 真值类别 | 命中 / 总数 | 准确率 |
|---|---|---|
| project | 4/17 | **23.5%** |
| preference | 4/7 | 57.1% |
| profile | 9/14 | 64.3% |
| decision | 11/15 | 73.3% |

混淆矩阵（行 = 人工判定，列 = 规则投票）：

```
               profile preferenc   project knowledge  decision
profile              9         3                             2
preference           2         4                             1
project              7         2         4                   4
decision             3                   1                  11
```

17 条真正的项目类条目，规则只认出 4 条，其中 7 条被误判成 `profile`、4 条被误判成 `decision`。

**原因不是权重调得不好，是关键词这个手段在 project 上不成立。** `classify.py:102-111` 给 project 配的词是 `github.com` / `仓库` / `项目` / `里程碑` / `进度` / `待办`。但真实的项目条目往往是「某文明模拟游戏，Android 上架为最终目标」这种写法——里面没有"项目"二字，全是语义。反过来，`仓库` 和 `项目` 这两个词在**指令类**文本里出现得更频繁（"新项目流程：理解目标 → 检查竞品"），于是权重 2 的弱词导致了双向误判。

项目条目靠内容识别，不靠词表。这一点用调权重救不回来。

## 三、25 条错误分成四类

| 类型 | 条数 | 占比 | 成因 |
|---|---|---|---|
| `fallback` | 12 | 22.6% | 无关键词命中，静默回落 `default` |
| `mixed` | 7 | 13.2% | 一条记忆含多个主题，单标签分类必然错 |
| `keyword` | 6 | 11.3% | 强词从别处抢走判定 |
| `fallback_hit` | 1 | 1.9% | 回落且恰好蒙对 |

### 1. fallback 是系统性误判，不是中性兜底

13 条 fallback 只对 1 条（7.7%）。这个数字低于"恒猜 profile"的基线，说明 fallback 抽到的**不是随机样本**——含"学校/专业/称呼"的 profile 条目本来就会命中关键词，根本进不了 fallback。能进 fallback 的恰恰是"无词可依"的条目，而它们主要是 `project` 和 `decision`。

所以 `classify(body, default)` 在无信号时静默返回 `default`，等于**把 22.6% 的样本批量推向错误答案，且不报错**。这是当前设计里最该先改的一处。

### 2. mixed 是切分粒度的后果，不是分类器的错

7 条混合条目（如"身份 + 对外口径"、"项目 + 要求"、"兴趣 + 边界"）无论换成什么分类器都会错，只要它是单标签。这是 `split_oversized()` 只按标题层级和字数切、不按**断言**切造成的：一个 400 字的段落里可以有四个独立事实，被当成一条记忆。

这一条同时解释了上一轮的争论：**切分和分类是耦合的**。切不细，分类必错；而"这里其实是两件事"恰恰是 LLM 明显强于正则判断的地方。

### 3. keyword 类：强词过度支配

`DECISIVE_WEIGHT = 3`（`classify.py:120`）让"绝不/禁止/铁律/必须/红线"等词一票定案。这是上一轮为修"先命中即赢"引入的，它修好了一个 bug，同时引入这一类错误：

- 项目清单条目里混了一句"绝不"，被判成 `decision`（`绝不(3) + 铁律(3) = 6 [decisive]`）
- 设备清单条目里有"不要"，被判成 `decision`（`不要(1) = 1`，对手一分没有）
- 协作规则条目里有"新项目流程"，被判成 `project`（`仓库(2) + 项目(2) + 待办(1) = 5`）

规律很清楚：**强词只在短条目上是强证据**。一条 400 字、含五个主题的段落里出现"绝不"，该考虑的是"这条该不该被拆开"，而不是"整条是 decision"。

## 四、这对上一轮的争论意味着什么

| 上一轮的判断 | 实测结果 |
|---|---|
| 「算法作为 floor 站得住，准确率应 >85%」 | ✗ 整体 52.8%，有信号 67.5% |
| 「AI 层可以排到阶段 3」 | ✗ 当前 floor 不达标，AI 层是必需品而非增强 |
| 「分类应该继续用算法，它便宜可解释」 | 部分成立：decision 73.3% 可接受，project 23.5% 不可接受 |
| 「真正该用 AI 的是去重和冲突检测」 | 需补充：**拆分（mixed）也是 AI 的强项，且优先级高于去重** |

我的判断错在把「算法可解释」当成了「算法够用」。可解释只解决"错了能不能看懂"，不解决"错多少次"。

## 五、待拍板的三项

以下都是设计变更，不定就不改代码：

1. **fallback 显式化为 `unknown`**：无信号时不再静默返回 `default`，而是标记"需判定"，强制进人工/AI 队列。改动最小，直接消掉 22.6% 的静默错误。
2. **AI 层前移，但只覆盖 fallback + keyword 两类**（19 条，35.8%）：规则处理有把握的部分，AI 只处理规则自认没把握的部分。这样成本可控，且每条仍可追溯是"规则判的还是 AI 判的"。
3. **先做拆分再做分类**：mixed 那 7 条说明顺序反了。让 AI 先答"这段里有几个独立事实"，再逐条分类，比直接分类更接近真实需求。

第 1 项我建议无条件先做；第 2、3 项改变阶段 3 的范围，需要你定。

## 六、本报告不成立的地方

- **标注是我做的**，不是 ground truth。53 条里有 7 条属于"混合条目，怎么标都说得通"，我把它们按"主信息"归了类。换一个人标，整体准确率可能浮动 ±5 个百分点。
- **样本只有 53 条，且来自同一个人的记忆库**。结论对这份库成立，不能外推成"中文记忆分类的普遍规律"。
- 类别体系本身可能缺项：`knowledge` 类在 53 条里一条都没有，长期职业路径类内容没有对应类别，被我硬塞进 `profile`。这是分类体系的问题，不是分类器的问题。
